✂️ Chunking Improvements

How you split documents directly determines retrieval quality. Better chunks = better answers.

📌

Contextual Retrieval New

Anthropic, Sep 2024 — reduces retrieval failures by 49%
High Impact Medium Effort 🛠 Existing Ollama

Before storing a chunk, call gemma2:2b with the full document + chunk text, asking it to write 1–2 sentences situating the chunk within the document. Prepend that context sentence to the chunk text before embedding and BM25 indexing. This gives each chunk the context it needs to be found even when the user asks about the broader topic rather than exact keywords. Anthropic measured 49% fewer retrieval failures using this approach, rising to 67% combined with reranking.

# src/ingestion/chunker.py — add to _chunk_post() def _add_context(self, full_doc: str, chunk: str, title: str) → str: prompt = f"""Document: {title} Content: {full_doc[:2500]} Chunk: {chunk} Write 1-2 sentences situating this chunk in the document context. Be concise.""" ctx = self.ollama.generate(model=config.llm_model, prompt=prompt)["response"].strip() return f"{ctx}\n\n{chunk}" # prepend before embedding
👪

Parent-Child Chunks New

Retrieve small, return large — best of both worlds
High Impact Medium Effort 🛠 ChromaDB metadata

Store two chunk sizes: small child chunks (300–400 chars) for precise semantic matching, and large parent chunks (1200–1500 chars) for rich LLM context. At query time, retrieve using child chunks (better precision), then look up their parent IDs and pass the full parent text to the LLM (better context). Currently both retrieval and generation use the same 1200-char chunk — this wastes precision.

# At ingestion: store parent metadata on each child chunk child_metadata = { "parent_id": f"{url_clean}_parent_{para_index}", "chunk_type": "child", ...existing_metadata } # At retrieval: after hybrid search on children, look up parents parent_ids = [c["metadata"]["parent_id"] for c in retrieved_children] parent_chunks = vector_store.get_by_ids(parent_ids)
🧠

Semantic Chunking

Split on embedding similarity drift, not character count
Medium Impact Easy Effort 🛠 langchain-experimental

Replace the 1200-char chunker with LangChain's SemanticChunker. It embeds each sentence with nomic-embed-text and splits when cosine similarity between consecutive sentences drops below a threshold — ensuring each chunk is semantically cohesive. Your current approach already respects paragraph boundaries which partially achieves this, so gains will be moderate but measurable.

pip install langchain-experimental from langchain_experimental.text_splitter import SemanticChunker from langchain_ollama import OllamaEmbeddings embeddings = OllamaEmbeddings(model="nomic-embed-text") chunker = SemanticChunker(embeddings, breakpoint_threshold_type="percentile") chunks = chunker.split_text(document_text)

Wire Up Existing multi_query() Already Coded

5 lines to activate — this is a free lunch
Medium Impact Easy (already implemented) 🛠 query_expansion.py

src/retrieval/query_expansion.py has multi_query() that generates 3 query variants — but enhanced_rag_chain.py never calls it. Wire it in: generate 3 variants, retrieve for each, deduplicate by chunk ID (union), then pass all unique chunks to the reranker. This costs 3× BM25+vector lookups but catches more recall. Combine with reranking to cut redundancy.

# enhanced_rag_chain.py — add to _retrieve() if self.use_multi_query: variants = self.expander.multi_query(query) # already exists all_chunks = [] seen_ids = set() for q in [query] + variants: for c in self.retriever.retrieve(q, top_k * 2): if c["id"] not in seen_ids: all_chunks.append(c); seen_ids.add(c["id"]) chunks = all_chunks # then rerank
🎯

Maximal Marginal Relevance (MMR)

Diverse results — avoid two near-identical chunks in the same prompt
Medium Impact Easy Effort 🛠 Built into ChromaDB

Currently if two chunks from the same blog post score high (e.g., post mentions AI in paragraph 1 and paragraph 4), both end up in the LLM prompt — redundant context that wastes tokens. MMR penalizes chunks that are too similar to already-selected chunks, ensuring diversity. ChromaDB supports this natively; LangChain's MMRRetriever wraps it cleanly.

FlashRank Reranking Top Priority

Sub-20ms CPU reranking of 50 candidates — designed for local use
High Impact Easy Effort 🛠 pip install flashrank

Bi-encoder embeddings (like nomic-embed-text) encode query and chunk independently — they cannot reason about their interaction. A cross-encoder takes both together and scores their relevance jointly, much more accurately. FlashRank is CPU-optimized (sub-20ms for 50 candidates) and uses ms-marco-MiniLM-L-12-v2 which downloads automatically on first use (~23MB). Insert after hybrid retrieval, before prompt building.

pip install flashrank # src/retrieval/reranker.py (new file) from flashrank import Ranker, RerankRequest class ChunkReranker: def __init__(self): self.ranker = Ranker(model_name="ms-marco-MiniLM-L-12-v2") def rerank(self, query: str, chunks: list[dict], top_k: int = 5) → list[dict]: passages = [{"id": c["id"], "text": c["text"]} for c in chunks] results = self.ranker.rerank(RerankRequest(query=query, passages=passages)) id_to_chunk = {c["id"]: c for c in chunks} return [id_to_chunk[r["id"]] for r in results[:top_k]] # enhanced_rag_chain.py — after hybrid retrieve, before prompt: chunks = self.reranker.rerank(query, initial_chunks, top_k=top_k) # retrieve 20, rerank to 5

📊 Evaluation Framework

You cannot measure what you do not measure. Add evaluation now and every future improvement becomes provable.

🧪

RAGAS with Ollama as Judge

Free, open-source RAG evaluation using your local LLM
High Impact Easy Effort 🛠 pip install ragas

RAGAS measures three key RAG dimensions automatically. By default it uses OpenAI as judge — but it fully supports Ollama as judge (free). Use your existing data/query_logs.db + data/feedback.db to build a ground truth test set from historically positive-feedback queries. Run nightly and track trends.

pip install ragas langchain-ollama from ragas import evaluate from ragas.metrics import faithfulness, answer_relevancy, context_recall from ragas.llms import LangchainLLMWrapper from langchain_ollama import OllamaLLM llm = LangchainLLMWrapper(OllamaLLM(model="qwen2.5:3b", base_url="http://localhost:11434")) result = evaluate(test_dataset, metrics=[faithfulness, answer_relevancy, context_recall], llm=llm) # Outputs: {"faithfulness": 0.87, "answer_relevancy": 0.91, "context_recall": 0.76}
Faithfulness
Does the answer stay grounded in retrieved chunks? Catches hallucinations.
Answer Relevancy
Does the answer address what was asked? Catches off-topic responses.
Context Recall
Did retrieval find the chunks needed to answer? Measures retrieval quality.
📁

Regression Test Set from Existing Logs

Your feedback.db already contains ground truth — use it
High Impact Easy Effort (no new libraries) 🛠 SQLite (existing)

Export queries with positive feedback from feedback_learning.db as (query, successful_chunk_ids) pairs. Run nightly: re-retrieve those queries and check if the same chunk IDs still rank in top-5. If recall drops after a change, you catch regressions before users do.

# scripts/regression_test.py import sqlite3 conn = sqlite3.connect("data/feedback_learning.db") test_cases = conn.execute(""" SELECT original_query, successful_chunks FROM query_mappings WHERE positive_count >= 2 """).fetchall() hits = 0 for query, chunks_json in test_cases: expected = json.loads(chunks_json) retrieved = retriever.retrieve(query, top_k=5) retrieved_ids = {c["id"] for c in retrieved} if any(e in retrieved_ids for e in expected): hits += 1 print(f"Regression recall: {hits}/{len(test_cases)} = {hits/len(test_cases):.0%}")

LightRAG — Graph + Vector Hybrid

For relationship-type queries: "What industries has Near Partner worked in?"
High Impact (for relationship queries) Hard Effort 🛠 pip install lightrag-hku + NetworkX

LightRAG extracts entities and relationships from your documents using the local LLM (works with Ollama), builds a NetworkX graph, and supports graph + vector hybrid retrieval. For Near Partner content it would extract entities like "Near Partner → provides → AI/ML services", "Near Partner → uses → Salesforce", etc. Standard vector RAG answers "what" questions well. Graph RAG additionally answers "how are things related" questions that span multiple documents. Defer until corpus grows to 200+ documents — for current size, standard RAG + reranking is sufficient.

pip install lightrag-hku networkx # Works with Ollama — no OpenAI key needed (unlike Microsoft GraphRAG) from lightrag import LightRAG from lightrag.llm.ollama import ollama_model_complete, ollama_embed rag = LightRAG(llm_model_func=ollama_model_complete, embedding_func=ollama_embed)
🎓

Domain Fine-Tuning (Long-Term)

Embed Near Partner knowledge into model weights using your feedback data
High Impact (long-term) Hard Effort 🛠 Unsloth / LlamaFactory (free, local)

After accumulating 500+ queries with feedback in data/feedback_learning.db, export them as synthetic Q&A training pairs and fine-tune SmolLM2-1.7B or Qwen2.5-1.5B using Unsloth (memory-efficient, CPU/consumer GPU). A fine-tuned model answers Near Partner-specific questions better and faster than a general-purpose model + RAG retrieval. This does not replace RAG for factual grounding — combine both.

⚠️

Long Context Window — Not Recommended for Production

Stuffing all content into context: tempting but impractical here
Medium Impact Easy to Try ⚠ CPU will struggle at 128K context

Models like llama3.1:8b support 128K context, theoretically allowing you to stuff the entire blog corpus into one prompt and skip retrieval. In practice: CPU inference at 128K context is 20–24× slower per token, "lost in the middle" degradation drops accuracy for facts in the middle of long contexts, and your Ollama setup would time out on most queries. Good for debugging (verify a specific answer exists in context), not for production.
